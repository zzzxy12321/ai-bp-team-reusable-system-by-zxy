# AIDT 项目目标

> 版本：V1.0  
> 定位：最高优先级项目目标与交付原则  
> 生效日期：2026-10-30  
> 适用范围：AIDT Demo、初期框架、正式开发、甲方复制和后续维护

## 🎯 核心目标

> **我的代码必须适合直接作为甲方便于复制、部署、接手和长期维护的正式代码仓库结构。**

AIDT 的 Demo 不是一次性演示目录，也不是按角色临时拼接的资料集合。Demo 必须是正式代码仓库的可运行纵向切片；后续开发必须在这套仓库结构、冻结技术栈和交付规范内持续演进。

## 📌 目标解释

“直接作为甲方便于复制和维护的正式代码仓库结构”具体包括：

1. 仓库只使用一套冻结技术栈。
2. 产品文档、后端源码、前端源码、数据库迁移、测试和部署资源分目录管理。
3. 后端与前端分别使用根级 `backend/` 和 `frontend/`，不混放在角色目录中。
4. 不在源码根目录使用“001-产品PRD、002-产品UI原型、003-前端代码、004-数据库脚本”这类角色分工目录代替工程结构。
5. 甲方可以通过统一仓库结构、README、AGENTS 规则和部署脚本理解、构建和运行系统。
6. 依赖版本集中锁定，离线环境可以恢复、构建、发布和部署。
7. 数据库结构变更通过迁移管理，不允许开发、DBA 和部署包各自维护不同版本。
8. 甲方差异通过配置、数据库或独立 Adapter 实现，不复制并长期维护不同代码分支。
9. 自动化测试、健康检查、备份恢复和回滚方案属于仓库交付物。
10. 临时文件、演示垃圾和私人工具配置不得进入正式提交。

## 🚫 不属于目标的输出

- 只供截图和汇报使用的静态页面。
- 按部门或岗位把源码拆成多个互不一致的目录。
- 为每个甲方复制一套随意修改的代码。
- 只交代码，不交数据库迁移、测试、部署和运维文档。
- 用临时目录、未锁定依赖或本地配置维持 Demo 运行。
- 把当前 Node.js + SQLite 验证版直接当作正式仓库。

## 🧭 决策优先级

当出现方案冲突时，按以下顺序判断：

1. 是否适合甲方便于复制、部署和长期维护。
2. 是否符合已冻结的技术栈与仓库结构。
3. 是否保留业务对象、流程、权限和审计边界。
4. 是否能够断网构建和恢复。
5. 是否能够通过自动化测试和回滚验证。
6. 最后才是演示速度、页面数量和局部开发便利。

## ✅ 目标检查问题

每个 Demo 或开发窗口开始前必须先回答：

1. 当前产出是否位于正式仓库结构中？
2. 是否使用了冻结技术栈？
3. 后端和前端是否分离？
4. 数据库变更是否进入迁移目录？
5. 是否包含测试、部署和回滚方案？
6. 是否能够在离线环境构建？
7. 是否存在只有当前开发机才能运行的隐含依赖？
8. 甲方复制仓库后，是否能由另一名工程师接手？

以上任一问题答案为“否”，不得将产出标记为正式交付基线。
