# AIDT 实施计划参考文档

> 版本：V1.2  
> 冻结状态：**已冻结（FROZEN）**  
> 冻结日期：2026-10-30  
> 定位：从验证版进入生产平台的阶段计划  
> 工期说明：以下周期是基于常见企业项目配置的建议值，不是在团队规模未知情况下的交付承诺
> 变更规则：阶段范围、目录结构、技术门禁和验收标准变更必须记录 ADR 或变更单

## 🧭 一、总体策略

采用“先底座、再样板、后领域、最后规模化”的路线：

1. 先冻结需求、数据权威和权限边界。
2. 先完成平台内核和三条跨部门样板。
3. 再做领域能力包和真实连接器。
4. 最后扩大工作台、数字员工和经营分析。

不采用“一次铺满十三个工作台”的方式。

### 1.1 项目目录与文件产出规划

#### 强制规则

1. 不再使用 `003.前端代码` 作为目录名。该目录实际包含后端和前端，必须拆分到根级 `backend` 与 `frontend`。
2. `AGENTS.md` 作为 AI 协作规则的唯一主文件，说明技术栈、目录边界、构建命令、测试命令和禁止事项。
3. `CLAUDE.md` 只保留必要的入口说明，并明确引用 `AGENTS.md`，避免两套规则长期漂移。
4. `.claude/` 等 AI 工具配置不得包含业务数据、密钥或生产配置；执行规则仍以 `AGENTS.md` 为准。
5. `docs` 目录可以保留中文和 `001—004` 编号，方便非技术角色阅读。
6. `backend`、`frontend`、`database`、`tests`、`deploy` 使用稳定英文目录，避免 PowerShell、NuGet、npm、CI 和部署脚本中的路径兼容问题。
7. 不在 `.csproj`、npm 包名、程序集名或服务名中使用中文编号。
8. `TMP.可删除` 不进入正式仓库，统一改为 `.tmp/` 并写入 `.gitignore`。
9. 任何角色不得在根目录自行新建业务源码目录；新增项目结构必须通过 ADR 评审。
10. 甲方定制内容不得直接修改核心代码；通过配置、数据库或独立 Adapter 项目实现。

#### 数据库脚本规则

1. EF Core 迁移是开发阶段数据库变更的源文件，统一放在 `database/migrations/`。
2. DBA 审核意见和生产发布脚本放在 `database/dba-review/`，不得另建互不一致的脚本版本。
3. 每次流程、对象或权限模型变化必须同步迁移脚本和对应测试。
4. 生产环境不得使用手工 SQL 绕过代码迁移修改表结构。
5. 发布包只包含经过审核并通过恢复演练的数据库迁移。
6. 迁移脚本必须支持重复校验、失败中止和版本记录。

#### 文档与代码的交付关系

```text
产品PRD → UI原型 → 系统设计/ADR → backend + frontend
                                   │
                                   ├─ database migrations
                                   ├─ tests
                                   └─ deploy package
```

产品文档不是代码仓库之外的临时材料，代码也不能脱离 PRD 和系统设计单独交付。甲方接收时必须同时得到需求、设计、源码、数据库迁移、测试和部署文档。

#### 规范先行门槛

正式业务开发前必须建立以下最小规范集：

1. `AGENTS.md` 和 `CLAUDE.md` AI 入口。
2. 项目目标、需求、冻结技术栈和计划。
3. AI 工程宪法、上下文阅读与恢复规范。
4. 架构与模块边界规范。
5. 后端、前端、数据库和 API 规范。
6. 安全、权限、审计、配置和事务规范。
7. 测试与回归规范。
8. Git、评审、部署和回滚规范。
9. 功能地图 V1 和首批模块 README。
10. 新功能、Bug、数据库、重构、发布和会话恢复提示词。

详细规范位于 `standards/`，模板位于 `templates/`，提示词位于 `prompts/`。

规范不要求一次性写完全部业务细节，但最小规范集必须在业务代码开发前完成。后续模块规范必须在对应模块开工前完成，不能以“代码先写、文档后补”为由绕过。

## 🏗️ 三、阶段 1：平台底座与三条样板

### 建议周期

8—12 周。

### 建设内容

#### 身份与权限

- 拒绝访问和越权审计

#### 对象与元模型

- 对象类型、字段和关系
- 状态机
- 动态表单
- 对象版本和变更历史
- 主数据引用

#### 流程与任务

- 流程定义和版本
- 流程实例
- 待办、通过、退回、终止
- 条件节点
- 会签、或签、转办和委托中的首期必需项
- SLA 和逾期升级

#### 审计与证据

- 关键动作审计
- 对象字段旧值/新值
- 任务决定和意见
- 外部写入证据结构
- 审计查询与导出

#### 工程与运维

- SQL Server 2025
- 数据库迁移
- 备份和恢复
- 日志、指标和告警
- 开发、测试和生产环境
- CI/CD 和自动化测试

### 三条样板流程

1. 客户样品到研发转产
2. 批次异常到处置和 CAPA
3. 请购到采购、到货检验和付款审批

### 外部系统策略

- 未获得接口和授权前继续使用 mock。
- 获得授权后先只读接入沙箱。
- 写入必须先做 dry-run、幂等和历史对账。
- 不在样板阶段直接产生真实付款或质量放行。

### 退出条件

- 三条流程均可以从发起走到完成。
- 退回和终止有自动化测试。
- 条件跳转有自动化测试。
- 权限越界被拒绝并有审计。
- 流程模板发布新版本后，历史实例仍按旧版本解释。
- 备份可以恢复，审计可以追溯。
- 外部系统状态标识清晰。
- 试点用户完成验收。

## ✅ 八、第一阶段 Definition of Done

### 产品

- 三个流程业务负责人确认流程口径
- PC 和移动端关键路径可用
- 未实现功能在界面上有明确状态

### 安全

- 未登录和越权访问被拒绝
- 字段级敏感数据有权限控制
- 密钥不进入源码
- 安全日志可查询

### 运维

- 监控、告警和日志可用
- 备份恢复验证通过
- 发布和回滚演练通过
- Mock、沙箱、正式和故障状态可区分

## ⚠️ 九、主要风险

| 风险 | 后果 | 应对 |
|---|---|---|
| 先铺页面、后补权限 | 返工和安全事故 | 身份权限进入第一里程碑 |
| 过早采用微服务 | 交付复杂、故障点增加 | 模块化单体起步 |
| 自研流程能力失控 | 会签、委托、版本和补偿难维护 | 冻结 Elsa Workflows，并先完成流程语义 PoC |
| 主数据口径未统一 | 报表和流程互相矛盾 | 设定数据责任人 |
| 外部接口迟迟不能提供 | 流程只能停留在 mock | 先只读沙箱和替代方案 |
| 数字员工权限过大 | 越权和不可逆风险 | 独立身份、短期令牌、人工确认和停止开关 |
| 把演示数据当真实数据 | 商密泄漏或决策错误 | 数据分级和 demo 标记 |
| 一次性承诺全量范围 | 工期失控和质量下降 | 以样板和阶段门验收 |
