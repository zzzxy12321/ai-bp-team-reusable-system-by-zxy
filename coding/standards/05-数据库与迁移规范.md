# 数据库与迁移规范

## 🎯 技术边界

- 数据库：SQL Server 2025。
- 主业务访问：EF Core。
- 报表、对账和复杂查询：Dapper。
- JSON 只用于动态扩展字段，不替代关系模型。
- 生产环境禁止使用 SQLite、PostgreSQL 或第二业务数据库。

## 🗂️ Schema 分区

不同模块使用独立 Schema：

| Schema | 责任 |
|---|---|
| `Identity` | 用户、组织、角色、权限和数据范围 |
| `Metadata` | 对象类型、字段、关系、状态机和视图 |
| `BusinessObject` | 主对象、版本和状态 |
| `Workflow` | 流程定义、版本、实例、任务和动作 |
| `Audit` | 审计和证据 |
| `Integration` | 连接器、命令、回执、Outbox 和对账 |
| `Agent` | 数字员工、Skill、运行和确认 |
| `Document` | 附件、版本和签名 |
| `Reporting` | 指标定义和聚合结果 |
| `Configuration` | 配置版本、发布和回滚 |

规则：

- 一张表只能有一个所有者模块。
- 其他模块不得直接写表。
- 跨模块查询通过 Application 契约、只读视图或 Reporting 模块。

## 🏷️ 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| Schema | PascalCase | `Workflow` |
| 表 | PascalCase、单数 | `WorkflowInstance` |
| 字段 | PascalCase | `CreatedAt` |
| 主键 | `Id` | `Id` |
| 外键 | 实体名 + `Id` | `WorkflowVersionId` |
| 主键约束 | `PK_表名` | `PK_WorkflowInstance` |
| 外键约束 | `FK_表_引用表` | `FK_WorkflowTask_WorkflowInstance` |
| 索引 | `IX_表_字段` | `IX_WorkflowTask_Status` |
| 唯一索引 | `UX_表_字段` | `UX_User_UserName` |
| 检查约束 | `CK_表_规则` | `CK_WorkflowInstance_Status` |
| 默认约束 | `DF_表_字段` | `DF_WorkflowInstance_CreatedAt` |

## 📏 字段类型

| 类型 | 规则 |
|---|---|
| 字符串 | `nvarchar`，按业务设置合理长度 |
| 长文本 | `nvarchar(max)`，不用于可搜索关键字段 |
| 日期时间 | `datetime2`，统一存 UTC |
| 金额 | `decimal(18,4)` 或按业务定义，禁止 `float` |
| 数量 | `decimal` 或整数，按业务精度定义 |
| 布尔 | `bit` |
| JSON | `nvarchar(max)` + `ISJSON` 检查，或 SQL Server 适用的 JSON 类型 |
| 版本号 | `rowversion` 或显式 `Version` |

禁止：

- 用 `varchar` 存中文。
- 用 `GETDATE()` 作为业务时间来源。
- 用浮点数计算金额。
- 用逗号分隔字符串保存关联关系。
- 将 SQL Server 的 `datetime` 代替 `datetime2`。

## 🔑 主键与业务标识

- 内部高频表优先使用 `bigint identity`。
- 需对外暴露或跨系统关联时增加稳定 `PublicId uniqueidentifier`。
- 业务编号不能替代主键。
- 业务编号必须唯一，但不得随业务含义变化修改。
- 外部系统 ID 必须保存来源系统和来源 ID。

## 🔗 关系与约束

- 所有必要关系建立外键。
- 不依赖应用层保证唯一性。
- 状态字段使用检查约束或状态查表。
- 关联表必须有唯一约束防止重复。
- 审计表不设置可级联删除的业务外键。
- 删除业务对象前必须定义保留和追溯策略。

## 🧾 JSON 字段

允许用于：

- 对象元数据定义
- 动态业务字段
- 流程变量
- 外部系统原始响应摘要

不允许用于：

- 用户、角色和权限关系
- 主对象之间的关系
- 流程实例与任务关系
- 审计、回执和幂等键
- 需要频繁筛选和排序的关键业务字段

含 JSON 的字段必须：

1. 有 `ISJSON` 检查。
2. 有 Schema 版本。
3. 有服务端验证。
4. 有迁移策略。
5. 关键查询字段单独结构化存放。

## 🔍 索引规范

- 外键列建立索引。
- 高频状态和日期组合建立复合索引。
- 唯一业务键建立唯一索引。
- 过滤条件与排序字段匹配。
- 低选择性字段不单独建立大量索引。
- 分页查询使用稳定排序，例如 `CreatedAt DESC, Id DESC`。
- 每次新增索引必须有对应查询场景和性能证据。

## 📦 分页与大数据量

- API 默认分页，不允许默认全表返回。
- `pageSize` 设置上限。
- 大表避免深分页，可使用游标或键集分页。
- 报表查询进入 Reporting 或只读查询，不阻塞业务事务。
- 批量导入必须分批提交并有失败回执。

## 🧬 对象版本

业务对象需要：

- 当前版本号
- 历史版本表或变更记录
- 字段级旧值/新值
- 修改人、时间、原因和 TraceId
- 来源系统和来源引用

流程实例必须保存：

- `WorkflowDefinitionId`
- `WorkflowVersionId`
- `BusinessObjectId`
- 启动时版本快照引用

禁止历史实例自动读取最新流程模板解释。

## 🧱 迁移规范

1. EF Core 迁移是开发阶段结构变更源文件。
2. 正式发布使用经过 DBA 审核的 SQL Server 迁移脚本。
3. 迁移文件进入 `database/migrations/`。
4. DBA 审核记录进入 `database/dba-review/`。
5. 生产环境禁止应用启动时自动迁移。
6. 部署脚本先备份，再执行迁移，再启动应用。
7. 迁移失败必须中止部署并恢复备份。
8. 迁移脚本必须可审计并记录执行版本。
9. 结构变更和代码发布必须保持向后兼容，避免滚动窗口不兼容。
10. 破坏性变更使用“扩展—迁移—收缩”三段式。

### 迁移任务必须说明

- 变更目的
- 影响表和数据量
- 锁表风险
- 预计执行时间
- 回滚方式
- 是否可在线执行
- 验证 SQL
- 相关代码和测试

## 🗑️ 删除规范

- 审计表禁止物理删除。
- 业务实体软删除必须使用 `IsDeleted`、`DeletedAt`、`DeletedBy`。
- 敏感数据删除需符合留存和审计要求。
- 清理任务必须保留操作记录。
- 级联删除必须显式定义，不依赖默认行为。

## 🧪 数据库测试

- 每个迁移在空库和上一版本库上各执行一次。
- 关键约束有数据库集成测试。
- 幂等键、版本和唯一约束有并发测试。
- 备份恢复在测试实例验证。
- 报表索引有执行计划或性能证据。

## 🚫 数据库反模式

- 直接手工改生产表
- 应用启动自动推迁移
- 无外键、无唯一约束
- 所有字段塞一个 JSON
- 用字符串拼接 SQL
- `SELECT *`
- 使用 `sa` 或共享数据库账号
- 删除审计数据
- 一个表被多个模块直接写
