# Bug 修复与重构规范

## 🎯 Bug 修复原则

Bug 修复必须解决根因，同时证明没有破坏邻近功能。禁止“先改几处看看”。

## 🐞 标准修复流程

### 1. 记录 Bug

```markdown
## Bug ID

## 现象

## 复现步骤

## 预期结果

## 实际结果

## 影响功能

## 环境

## 日志和 TraceId

## 最近相关变更
```

### 2. 复现

- 使用最小步骤复现。
- 保存失败状态或失败测试。
- 不允许直接根据报错猜修复。

### 3. 定位

通过功能地图查：

- 页面
- API
- 用例
- 领域规则
- 数据表
- 权限
- 工作流
- 测试

回答：

1. 错误在哪一层产生。
2. 为什么现有测试没有发现。
3. 哪些调用方受影响。

### 4. 写失败测试

优先新增自动化测试。无法自动化时，写可重复验证步骤。

### 5. 最小修复

- 只修改根因相关代码。
- 不顺便重构整个模块。
- 不顺便升级依赖。
- 不修改无关格式。
- 不删除失败测试。

### 6. 回归

运行：

- 失败测试
- 当前功能测试
- 邻近功能测试
- 权限测试
- 关键 E2E

### 7. 记录

更新：

- 功能地图
- 回归用例
- `progress.md`
- 变更说明

## 🚦 修改预算

默认 Bug 修复修改不超过 5—8 个文件。超过时：

- 重新评估根因
- 拆分修复任务
- 写 ADR 或变更计划

不可为了“一次清干净”引入大范围行为变化。

## 🧹 重构规范

### 重构前提

- 有现有测试保护
- 不改变外部行为
- 目标明确，例如消除重复、调整边界、降低耦合

### 重构流程

1. 记录当前行为。
2. 确认测试基线通过。
3. 小步修改。
4. 每一步运行测试。
5. 不混入新功能和 Bug 修复。
6. 对照公共契约检查兼容性。
7. 完成后更新模块 README 和 ADR。

### 重构边界

一次重构只处理一个边界：

- 模块边界
- 分层边界
- 数据结构
- 前端组件
- 接口契约

不能同时重构模块、数据库和前端状态。

## 🔄 长任务拆分

超过以下任一条件应拆分：

- 涉及三个以上业务模块
- 修改超过 10 个业务文件
- 同时需要数据库迁移和 API 升级
- 同时修改前后端和外部 Adapter
- 预计无法在一次会话中完成和验证

拆分顺序：

1. 契约和数据结构
2. 后端最小闭环
3. 前端接入
4. 迁移与兼容
5. 完整回归

## 🧯 回滚

Bug 修复和重构必须有回滚方式：

- 代码回滚
- 配置回滚
- 数据库兼容
- 外部命令补偿

如果无法回滚，必须在实施前说明原因和风险。

## 🚫 反模式

- 没复现就修改
- 一次改动多个无关问题
- 删除测试让 CI 变绿
- 吞异常
- 增加全局 try/catch 掩盖错误
- 关闭类型检查
- 批量升级依赖
- 只修前端显示不修后端根因
- 只修后端不考虑前端旧客户端
