# 功能地图与影响分析规范

## 🎯 为什么需要功能地图

代码规模变大后，AI 的主要问题不是不会写代码，而是：

- 不知道功能在哪里
- 不知道应该读哪些文件
- 不知道修改会影响什么
- 修一处后破坏其他功能

功能地图是“业务功能到技术资产”的索引，也是 AI 上下文选择器。

## 🗺️ 功能地图位置

```text
docs/project/FEATURE_MAP.md
```

如果功能较多，按模块拆分：

```text
docs/project/features/
├─ workflow.md
├─ business-object.md
├─ audit.md
├─ agent.md
└─ integration.md
```

## 🧾 每个功能的必备字段

| 字段 | 说明 |
|---|---|
| Feature ID | 稳定编号，例如 `WF-001` |
| 功能名称 | 业务可理解名称 |
| 业务目标 | 解决什么问题 |
| 状态 | planned / active / deprecated |
| 页面/路由 | Vue 页面和 URL |
| 前端目录 | feature、components、store |
| 后端模块 | Application、Domain、API |
| API | 端点和 OpenAPI operationId |
| 数据表 | 主表和关联表 |
| 流程定义 | Workflow Code/Version |
| 权限 | 菜单、接口、数据范围 |
| 审计事件 | 关键动作 |
| 外部系统 | Adapter 和方向 |
| 测试 | 单元、集成、E2E、回归 |
| 关键文档 | PRD、ADR、模块 README |
| 已知风险 | 并发、敏感数据、兼容性 |
| 负责人 | 产品或模块负责人 |

## 🧩 模块 README

每个 `backend` 模块和 `frontend/features` 模块必须有 `README.md`，说明：

- 模块目的
- 允许依赖
- 禁止依赖
- 公共入口
- 拥有的数据表
- 发布的事件
- 订阅的事件
- API
- 关键状态
- 测试位置
- 已知限制

模块 README 是 AI 进入模块的第一入口，不允许只写一句“本模块负责业务”。

## 🔍 变更影响分析

在编码前填写：

```markdown
## 变更目标

## 涉及功能 ID

## 预期修改文件

## 上游调用方

## 下游依赖

## API 变化

## 数据库变化

## 权限变化

## 审计变化

## 前端状态变化

## 测试范围

## 回归风险

## 回滚方式
```

### 影响检查顺序

1. 需求
2. 页面和路由
3. API 契约
4. Application 用例
5. Domain 规则
6. 数据库表和迁移
7. 权限和审计
8. 前端 store 和 API client
9. 自动化测试
10. 部署和配置

## 🕸️ 依赖关系

每个功能至少记录：

```text
Page → API Client → API Endpoint → Application Use Case
     → Domain Rule → Repository → SQL Table
     → Audit Event → Tests
```

如果跨模块：

```text
Module A → public contract/event → Module B
```

禁止文档出现：

```text
Module A → direct SQL write → Module B table
```

## 🔄 更新规则

功能地图必须在以下变化时更新：

- 新增或删除功能
- 路由变化
- API 变化
- 数据表变化
- 权限变化
- 审计事件变化
- 工作流版本变化
- 测试入口变化
- 功能废弃

未更新功能地图的代码变更不能标记完成。

## 🤖 AI 使用方式

AI 开始任务时：

1. 先找到功能 ID。
2. 只读取该功能的模块 README 和关联文件。
3. 根据影响分析扩展上下文。
4. 若找不到功能，先登记，不直接猜代码位置。

AI 完成任务时：

1. 更新功能地图。
2. 记录新增或变化的文件和测试。
3. 标记新的回归风险。

## 🚫 反模式

- 功能地图只是页面清单
- 只记录前端，不记录表、API 和测试
- 功能地图长期不更新
- 功能 ID 随版本改名
- AI 在全仓库盲搜而不是先查地图
- 用模块名称代替真实调用链
