# Vibecoding 标准工作流

## 🎯 目标

让 AI 在有限上下文和多人协作环境中，按同一套流程执行任务，减少遗漏、幻觉、范围蔓延和回归。

## 🧭 总体流程

```text
接任务
 → 读目标与规范
 → 查功能地图
 → 建上下文包
 → 做影响分析
 → 写实施计划
 → 编码
 → 测试
 → 自审
 → 更新文档
 → 提交/部署建议
 → 会话交接
```

## 0. 接收任务

先判断任务类型：

- 新功能
- Bug 修复
- 数据库变更
- API 变更
- 前端重构
- 架构重构
- 发布部署
- 纯文档

不同类型使用不同模板。

## 1. 读取最小上下文

必读：

- 项目目标
- 需求和冻结技术栈
- AI 工程宪法
- 上下文阅读规范
- 当前计划、发现和进度
- 功能地图中的相关条目

## 2. 建立上下文包

上下文包只包含：

- 当前目标
- 验收标准
- 相关功能 ID
- 相关模块 README
- 相关 API
- 相关数据表
- 相关页面
- 相关测试
- 已知风险和最近变更

禁止把整个仓库作为上下文包。

## 3. 变更影响分析

编码前输出：

- 要改什么
- 为什么要改
- 哪些文件预期修改
- 哪些文件明确不修改
- 哪些模块和调用方受影响
- 哪些测试证明安全
- 回滚方式

影响分析写入 `task_plan.md`。

## 4. 输出实施计划

计划至少分为：

1. 契约/数据结构
2. 后端实现
3. 前端实现
4. 测试
5. 文档
6. 部署影响

每一步都有验证方法。

## 5. 编码

- 每次只处理一个可控步骤。
- 使用项目模板和公共能力。
- 不新增未评审依赖。
- 不跨模块直接操作数据。
- 不修改无关格式。
- 不在同一任务夹带升级和重构。

## 6. 测试

按变更类型运行最小完整集合：

- 单元
- 集成
- API
- 流程
- 前端
- E2E
- 离线构建

测试失败先修根因，不修改断言掩盖问题。

## 7. 自审

AI 必须进行三次不同视角审查：

### 架构审查

- 分层
- 模块依赖
- 数据所有权
- 技术栈

### 行为审查

- 成功
- 失败
- 空值
- 并发
- 权限
- 超时

### 交付审查

- 测试
- 文档
- 迁移
- 配置
- 回滚

## 8. 更新文档

按变更更新：

- 功能地图
- 模块 README
- OpenAPI
- 数据模型
- ADR
- README/部署说明
- progress/findings

## 9. 会话交接

结束前写：

- 已完成
- 修改文件
- 测试结果
- 未完成
- 风险
- 下一步

## 🛑 强制暂停条件

出现以下情况必须停止并请求确认：

- 需要更换技术栈
- 需要跨模块大范围重构
- 数据库需要破坏性变更
- 需要真实外部系统写回
- 涉及付款、质量放行、配方和 DCS
- 规范与用户指令冲突
- 三次修复仍失败
- 无法证明回滚

## 🧠 上下文丢失时的恢复

不要凭记忆继续。先读：

1. `task_plan.md`
2. `findings.md`
3. `progress.md`
4. Git diff
5. 功能地图
6. 相关测试

恢复后再继续。

## 🚫 AI 反模式

- 一上来写代码
- 读全仓库
- 同时改很多文件
- 猜 API 和表结构
- 自创架构
- 只测成功路径
- 改测试掩盖错误
- 不更新文档
- 把计划写成结果
