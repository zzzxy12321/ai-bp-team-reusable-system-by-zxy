## 🧭 一句话结论

**有条件可行。** AIDT 的产品目标和对象—流程—事件—审计—数字员工治理方向是自洽的，现有 MVP 也已真实跑通核心闭环；但当前“Node.js 24 原生 HTTP + 内置 SQLite + 原生 HTML/CSS/JS”只适合方案验证和交互演示，**不能直接作为成熟生产网站的技术栈**。

最终判定：

| 判断项 | 结论 | 说明 |
|---|---|---|
| 产品需求是否能实现 | ✅ 可以 | 业务范围大，但可以按平台内核、领域能力包和试点流程分阶段建设 |
| 当前业务闭环是否成立 | ✅ 已成立 | 对象、流程、条件、退回、终止、审计和数字员工确认均跑通 |
| 当前代码是否可做演示 | ✅ 可以 | API 和浏览器自动化复测通过 |
| 当前技术栈是否可直接上线 | ❌ 不可以 | 缺少正式身份权限、生产数据库治理、流程版本、备份恢复和安全运维 |
| 当前系统设计是否足够成熟 | ⚠️ 部分成立 | 原则正确，但缺少生产级模块边界、数据模型、集成可靠性和非功能设计 |
| 12—18 个月路线是否可承诺 | ⚠️ 暂不能 | 团队规模、预算、外部接口、部署和安全等级尚未确认 |

### 匹配良好的部分

| 需求 | 当前实现或设计 | 判断 |
|---|---|---|
| 对象先行 | `business_objects` 保存主对象，流程使用 `object_id` 引用 | ✅ 方向正确 |
| 能力复用 | 元数据对象、流程模板、任务、审计、数字员工统一实现 | ✅ 原型中成立 |
| 条件流程 | 支持金额和风险等级条件进入/跳过 | ✅ 可验证 |
| 数字员工治理 | 独立 Agent、等级、范围、禁止动作、人工确认、运行审计 | ✅ 原型中成立 |
| Mock 边界 | UI、健康接口、业务契约均明确标识模拟 | ✅ 可信 |
| 自动化验证 | API 和浏览器均有真实执行脚本 | ✅ 高于静态原型 |
| 文档与实施方法 | 已区分需求、契约、迁移、测试和边界 | ✅ 有助于后续重写 |

### 当前技术栈不适配成熟要求的部分

| 成熟网站要求 | 当前状态 | 影响 |
|---|---|---|
| 正式登录与 SSO | 无真实认证；健康接口明确标注为 demo identity | 阻断上线 |
| 权限与数据范围 | 页面上显示角色，但 API 不校验真实身份；操作人由请求体传入 | 严重安全风险 |
| 流程版本快照 | 流程实例按 `workflow_code` 读取当前模板，未固定实例启动时的版本 | 模板变更会影响历史实例语义 |
| 复杂审批语义 | 单体线性步骤数组；缺少会签、或签、加签、转办、委托、定时器、补偿 | 不足以覆盖跨部门流程 |
| 审计可信性 | 审计写入普通 SQLite 表；操作人可伪造；重置接口无鉴权 | 不能作为正式质量或电子证据 |
| 数据关系与主数据 | 字段存 JSON，缺少对象关系、主数据映射、字段级敏感等级和引用完整性 | 13 个工作台规模化后难治理 |
| 数据库迁移 | `CREATE TABLE IF NOT EXISTS` 与临时 `ensureColumn` | 不适合生产发布和回滚 |
| 备份恢复 | 有 WAL，但没有备份、PITR、恢复演练与 RTO/RPO | 不满足关键业务系统 |
| 高可用与监控 | 单进程、无指标、追踪、告警、灾备 | 无法定义生产 SLA |
| 连接器可靠性 | 只有 mock 目录和契约说明 | 真实集成尚不可用 |
| 列表与查询 | 多数接口一次返回全量数据，无分页和筛选 | 数据增长后性能不可控 |
| 前端工程化 | 原生单页应用、集中式状态、无路由和类型契约 | 难以承载 13 个工作台和多人协作 |
| 安全基线 | 无 CSRF、CSP、安全响应头、登录限流和越权审计 | 生产安全检查不通过 |

### 结论

现有技术栈不是“方向错了”，而是“层级选错了”。它在验证架构假设上是合理选择，在产品化后继续沿用则会造成安全、治理和扩展债务。**可以保留业务契约、数据语义和交互原型；应当重写生产代码，而不是在原单文件上无限加功能。**

## 🏗️ 推荐目标技术栈

推荐采用“模块化单体起步、异步能力内聚、后续按瓶颈拆分”的架构。AIDT 目前最大的风险是业务复杂度、权限边界和流程一致性，不是流量；第一期不应采用微服务造成分布式事务和运维负担。

### 推荐基线

| 层 | 推荐方案 | 选择理由 |
|---|---|---|
| 后端 | Java 21 LTS + Spring Boot 3.x | 企业生态成熟，事务、权限、连接器和长期维护能力更稳 |
| 应用结构 | 模块化单体，按身份、对象、流程、任务、审计、连接器、Agent 分模块 | 高内聚低耦合，可后续拆分，不引入过早微服务 |
| 数据库 | PostgreSQL 16+ | 事务、JSONB、行级安全、索引、备份和可扩展性适合元模型与业务数据 |
| 流程引擎 | 优先评估 Flowable 7；Camunda 7 类 BPMN 引擎作为备选 | 需要 BPMN、人工任务、会签、定时、版本、回滚和生产验证 |
| 缓存与短期协调 | Redis | 会话、幂等占位、限流、短期锁和缓存；业务主数据不依赖 Redis |
| 异步消息 | RabbitMQ/Kafka 中选一；第一版可先采用事务 Outbox | 外部事件、通知、Agent 任务和连接器重试需要可靠投递 |
| 文件与证据 | S3 兼容对象存储，如 MinIO | 附件、签名证据、导入文件和文档版本不塞数据库 |
| 前端 | React + TypeScript + Vite；企业组件库可选 Ant Design Pro | 组件、表单、权限路由、复杂表格和大型团队协作更成熟 |
| 移动端 | 响应式 Web 为第一期；确需扫码/离线时再做 PWA 或独立页面 | 先验证业务，避免同期维护多端 |
| 身份认证 | 企业 IdP + OIDC/SAML；钉钉作为入口之一 | AIDT 内部负责授权，不自行发明身份体系 |
| 连接器 | 独立连接器模块 + OpenAPI 契约 + Outbox + Dead Letter | 统一认证、映射、重试、对账、补偿和监控 |
| 可观察性 | OpenTelemetry + Prometheus/Grafana + Loki 或同类 | 监控流程、接口、任务和 Agent 运行 |
| 部署 | Linux 容器；首期虚拟机/容器编排均可，生产建议双实例和独立数据库 | 满足可发布、可回滚、可备份和可扩容 |
| 数据仓库 | 第一阶段暂缓；出现跨系统分析需求后引入 PostgreSQL 只读副本或湖仓 | 避免过早搭大数据平台 |
| 时序数据 | DCS 接入阶段引入 TimescaleDB/工业历史库 | 高频参数不能进入普通业务表 |

### 如果团队只擅长 JavaScript

可采用 “NestJS + PostgreSQL + React + Flowable REST/独立 BPM 服务” 的组合。它是可行替代方案，但仍需正式认证、数据库迁移、权限、审计、队列和运维；不能把当前原生 Node 服务直接扩展成生产平台。

### 不推荐

- 用 SQLite 作为生产主数据库。
- 把 MongoDB 作为唯一业务主库，再靠应用代码补事务和关系。
- 一开始拆成十几个微服务。
- 用纯自定义状态机替代成熟流程引擎，却又要做会签、委托、定时、版本和补偿。
- 只做静态 HTML 或大屏，没有真实业务流程、权限和审计。

## 🗺️ 推荐系统设计

### 逻辑结构

```text
PC 管理端 / 专业工作台 / 一线移动端
                    │
               API Gateway
                    │
        AIDT 模块化单体或核心服务
 ┌──────────┬──────────┬──────────┬──────────┐
 │ 身份权限 │ 对象与元模型 │ 流程与任务 │ 审计与证据 │
 ├──────────┼──────────┼──────────┼──────────┤
 │ 通知事件 │ 连接器与对账 │ 文档与签名 │ 数字员工运行时 │
 └──────────┴──────────┴──────────┴──────────┘
          │             │              │
       PostgreSQL    Redis/队列     MinIO/对象存储
          │
  U9 / ERP / DCS / WMS / LIMS / 钉钉 / 企业 IdP
```

### 核心数据模型

至少要独立建模：

- `organizations`、`users`、`roles`、`permissions`、`data_scopes`
- `object_types`、`field_defs`、`object_relations`
- `business_objects`
- `workflow_definitions`、`workflow_versions`、`workflow_instances`
- `tasks`、`task_candidates`、`task_actions`
- `events`、`outbox_events`、`dead_letters`
- `connectors`、`connector_commands`、`connector_receipts`、`reconciliations`
- `agent_profiles`、`agent_runs`、`agent_confirmations`
- `audit_events`、`evidence_assets`
- `attachments`、`signatures`、`document_versions`

关键规则：

1. 流程实例必须固定启动时的 `workflow_version_id`。
2. 业务字段可以允许 JSONB，但主键、关系、状态、权限、流程引用和审计必须结构化。
3. 业务对象修改需要保存字段级旧值/新值和版本。
4. 审计表只追加，不允许普通业务接口更新或删除。
5. 外部命令必须有 `command_id + idempotency_key + approval_evidence + receipt`。
6. 所有跨系统事件通过 Outbox 投递，失败进入死信和人工补偿队列。

### 工作流引擎必须覆盖

- 串行审批
- 会签、或签
- 加签、转办、委托
- 退回、撤回、终止
- 定时器、SLA、逾期升级
- 条件与决策表
- 子流程
- 版本冻结
- 失败重试、补偿和人工接管
- 运行回放与审计

如果市售或开源流程引擎无法满足 AIDT 的业务语义，必须在选型验证阶段明确差异和扩展方式，而不是默认自研一套不完整状态机。

### 权限设计

至少分为四层：

1. 组织/部门范围。
2. 项目/客户/批次等业务范围。
3. 字段敏感等级。
4. 动作权限，例如读取、生成草稿、提交、审批、写回、付款申请。

数字员工必须有独立服务身份和短期授权令牌。Agent 无权直接复用真人会话；人工确认必须绑定真实登录身份、签名意图和流程版本。

## 🔍 对抗式审查

### 1. “原型已经跑通，所以生产也能这样做”

**不成立。** 原型验证的是业务语义，不是生产属性。当前任务并发和幂等做得不错，但身份可伪造、审计可被普通接口重置、流程版本不冻结，这些在演示中不暴露，在生产中是阻断项。

### 2. “先做 13 个工作台，页面齐了平台就成熟”

**不成立。** 真正决定复用率的是对象、关系、状态、权限、流程模板和领域能力包。直接铺工作台会把配置债务放大 13 倍。

### 3. “自研轻量流程就够”

**短期可变，长期风险高。** 金额审批和简单退回够用；一旦出现会签、委托、SLA、加签、版本同步和补偿，自研成本会快速上升。应先做引擎 PoC 再决策。

### 4. “PostgreSQL 加 JSONB 就能不建关系模型”

**不成立。** JSONB 适合动态字段，不适合替代关系、引用完整性、权限索引和关键业务字段。应采用“稳定关系字段 + JSONB 动态扩展”的混合模型。

### 5. “AI 数字员工以后再加治理”

**不成立。** 身份、权限、确认、审计和停止开关必须从第一天设计。当前 MVP 已经把这些作为展示字段，但还没有真正的授权令牌、工具沙箱和模型调用控制。

### 6. “12—18 个月一定完成全量蓝图”

**当前无法证明。** 没有团队人数、预算、业务专家投入、外部接口可用性和生产合规要求。更合理的是先承诺 90 天平台底座与三条样板链，按月复盘后逐阶段扩展。

## 🚨 P0 阻断项

以下任一项未完成，不应承载真实业务数据：

1. 正式认证、SSO、会话和权限校验。
2. API 级 RBAC/ABAC 和字段级数据范围。
3. 流程定义版本冻结与实例语义隔离。
4. 审计不可篡改、拒绝访问也记录、操作者来自可信身份。
5. 数据库版本化迁移、生产备份和恢复演练。
6. 外部连接器的幂等、重试、死信、对账和补偿。
7. 敏感数据分级、加密、密钥管理和模型路由。
8. 生产部署、监控、告警、回滚和应急接管。

## 🛠️ 实施路线

### 第 0 阶段：决策冻结与 PoC（2—3 周，工期随团队规模调整）

- 确认部署、身份、BPM、数据库和试点部门。
- 用脱敏样例完成 Flowable 流程语义 PoC。
- 完成一个真实接口的只读契约验证，不写生产系统。
- 输出权限矩阵、数据分级、审计留存和 RTO/RPO。

### 第 1 阶段：平台底座与三条样板（建议 8—12 周）

- 身份、权限、对象、动态表单、流程、任务、审计。
- 三个跨部门样板流程。
- PC 专业工作台和移动基础视图。
- 数据库迁移、审计、备份恢复、监控和测试流水线。
- 所有外部系统保持 mock 或只读沙箱，不产生真实副作用。

### 第 2 阶段：领域能力包（约 3—6 个月）

- 研发实验、批次质量、采购供应链优先。
- 建立主数据与指标口径。
- 接入 U9/ERP/DCS 沙箱和正式对账。
- 配置发布、沙箱、影响分析和回滚。

### 第 3 阶段：数字员工与规模化（约 6—12 个月）

- Agent 运行时、Skill 版本、评测、预算、工具沙箱和停止开关。
- 经营指标、知识检索和跨系统协同。
- 多组织、多工厂和高可用扩展。

> 上述时间不是承诺值。实际排期必须结合团队人数、外部接口交付和业务专家可用性重新估算。

## ✅ 最终可执行建议

1. **保留现有业务契约和原型，不保留其生产技术栈。**
2. **先选择一个正式生产底座，再进入领域功能开发。**
3. **推荐 Java + PostgreSQL + Flowable + React 的模块化单体方案。**
4. **第一阶段只承诺 90 天平台底座与三条样板流程，不承诺 13 个工作台全量上线。**
5. **把身份权限、流程版本、审计可信、连接器可靠性和备份恢复列为上线门槛。**
6. **外部系统没有接口资料和授权前，继续使用明确标注的 mock，不制造“已打通”的假象。**
