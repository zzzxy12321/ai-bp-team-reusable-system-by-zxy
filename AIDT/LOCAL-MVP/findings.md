# 发现与决策

## 2026-10-27 目标模式基线审计
- 现有语法、API、浏览器基线全部通过，历史测试证据对应真实可运行实现，不是静态页面。
- 当前数据库只有 `object_defs`（对象定义）而没有业务对象实例表；业务字段实际复制在 `workflow_instances.payload_json`。这违反“流程引用对象，不复制对象”。
- 当前任务动作已能推进、退回和终止，但测试只证明“通过”，没有对退回/终止/重复动作/并发推进进行验证。
- 当前采购测试只证明 68,000 元会进入重大审批，没有证明低金额会自动跳过条件节点。
- 当前输入校验只检查标题和流程是否存在，没有按对象字段元数据校验必填、类型、枚举和未知字段。
- 当前发起流程没有幂等键；重复请求可产生重复对象和流程实例。
- 当前数字员工有独立身份、等级、范围、免责声明和审计，但“需人工确认”没有对应确认接口、状态与证据。
- 当前流程卡片只有摘要，没有实例详情；对象卡只有元数据，没有对象实例、关联流程和审计。
- 当前浏览器移动端测试是在桌面启动后动态改视口，未验证移动端首次加载与侧栏交互。

## 本轮实现决策

| 决策 | 理由 |
|---|---|
| 新增 `business_objects` 主对象表 | 让流程只保存 `object_id`，从数据库约束层面落实对象先行 |
| 现有演示数据一次性迁移为对象记录 | 保留可运行性，同时移除流程实例内的业务字段副本 |
| 发起接口支持 `Idempotency-Key` / `idempotencyKey` | 同键同请求返回同一实例，同键不同请求返回 409 |
| 任务动作使用条件更新和事务内重读 | 防止重复点击或并发请求重复推进流程 |
| 必填/类型/枚举/未知字段在服务端校验 | 浏览器 required 只能改善体验，不能作为业务边界 |
| 数字员工运行先进入 `pending_confirmation` | “需人工确认”必须有可验证动作，不能只显示文案 |
| 增强项严格限定为流程详情和对象详情 | 两项直接提升跨对象、任务和审计的可追溯性 |

## 已完成验证结论
- 业务对象已与流程实例解耦：样品测试实例引用独立对象，对象状态最终为 `已转产`，版本从 1 增至 7。
- 三条业务链完整走到结束：样品到转产 6 节点；低金额采购 6 节点并跳过重大审批；高金额采购 7 节点并进入重大审批。
- 客诉链路验证“第二节点退回首节点”后实例继续运行，再在首节点终止后实例 `rejected`、对象 `已终止`。
- 同一任务两个并发请求只允许一个 200，另一个返回 409；发起幂等键重放返回同一实例，内容冲突返回 409。
- 字段校验覆盖必填、未知字段、错误数字类型和非法日期，均返回稳定 422 错误码。
- 数字员工跨流程访问返回 403；A2 运行等待人工确认，确认后记录确认人并写 `agent.confirmed` 审计。
- 浏览器真实点击任务并通过，任务记录增加、实例当前节点前进、保留一个待办、审计增加 3 条。
- 桌面 1440px 与移动 390px 均无横向溢出；浏览器未捕获异常和 `console.error` 均为 0。
- 最终演示数据重置后，SQLite `integrity_check=ok`、外键无违规、4 对象/4 实例/4 待办/9 审计。

## 需求
- 用户希望基于现有 AIDT 企业业务操作系统蓝图编写一套“目标模式提示词”。
- 最终技术栈未拿到，但已确认运行环境为 Windows。
- 用户希望今晚先运行本地初始版本，明早查看结果。
- 需要验证各部门通过既有能力自定义流程，而不是每个部门开发独立后端。
- 需要为未来 U9、ERP、DCS、钉钉、数字员工和定时 Skill 保留扩展边界。

## 研究发现
- 参考 HTML 已覆盖战略、数据边界、元模型、业务板块、流程样板、系统集成、数字员工和治理路线。
- 一晚无法合理完成全量 13+ 业务工作台，必须先做可证明架构成立的纵向样板。
- 本机 Node.js v24.18.0 可用，`node:sqlite` 已验证可以创建表、写入和查询。
- 本机 .NET 不可用；Java 17 可用，但零第三方依赖启动速度不如 Node 原生方案。
- 当前应采用“业务契约优先、临时技术栈其次、最终栈可替换”的策略。

## 技术决策
| 决策 | 理由 |
|------|------|
| 本地版使用 Node 内置 HTTP 与 SQLite | 零安装、Windows 可启动、数据持久化、便于明早直接验收 |
| 前端使用原生 HTML/CSS/JS 单页应用 | 不受 Node 框架和构建工具锁定 |
| 连接器抽象为 provider 接口 | 当前使用 mock provider，未来换真实 U9/ERP/DCS adapter |
| 流程引擎使用最小状态机 + 任务节点 | 足够验证事件、条件、审批、回退和审计 |
| 数字员工登记独立身份、权限、执行等级和人工确认点 | 防止用真人账号或无限工具权限代替治理 |
| 不实现真实文件上传、邮件发送和外部系统写回 | 今晚无授权、无接口，且不应产生真实副作用 |

## 当前本地 MVP 范围
1. 工作台汇总：对象、流程、待办、数字员工、审计数量。
2. 元数据：业务对象定义、字段定义、状态机。
3. 流程模板：研发样品、批次异常、采购到付款、客诉到CAPA。
4. 流程实例：发起、推进、审批、退回、完成、审计。
5. 待办中心：按角色过滤、处理任务。
6. 数字员工：登记、A0-A4执行等级、权限范围、模拟运行记录。
7. 连接器监视：U9/ERP/DCS/DingTalk 的 mock 状态和接口契约。
8. 所有动作生成本地审计事件。

## 明确不做
- 不做生产级登录、SSO、电子签名合规认证。
- 不连接真实U9、ERP、DCS或发送外部消息。
- 不实现全量13个部门页面。
- 不自称通过财务、GMP、等保或任何法定合规认证。
- 不自动生成或修改配方数据。

## 遇到的问题
| 问题 | 解决方案 |
|------|---------|
| 最终技术栈未知 | 采用适配器边界和可迁移契约，不把临时栈当最终决策 |
| 一晚时间有限 | 锁定六项平台内核能力，业务域只做四个代表性样板 |
| 当前无真实系统接口 | 使用 mock provider 和明确的接口契约，不制造“已打通”的假象 |
| 旧流程数据复制对象字段 | 新增业务对象表、回填旧实例 `object_id`、清空流程 payload 副本 |

- 本地MVP沿用同一品牌逻辑，但采用更适合操作系统的左右布局、数据表和任务卡片。
- 第一次浏览器渲染停在加载层，原因是 `btnSidebar` 与实际 `sidebarToggle` 元素ID不一致，导致后续初始化中断。
